# Forfaits : règles et pièges du projet

- Dépôt PUBLIC (site GitHub Pages) : jamais de vrais forfaits, de vrais prix, de vrais noms de produits (même dans les exemples et les tests : noms inventés comme Zorba, Kalpo, T1 DEMO) ni le nom de l'entreprise. Les exports (`forfaits-*.json`, `*.csv`) et `prive/` sont ignorés par git ; ne pas forcer leur ajout.
- Après toute modification du `<script>` de `index.html` : `python outils/csp.py`, sinon le navigateur bloque le script (page vide). `test_empreinte_de_securite_a_jour` le vérifie.
- Pas de `innerHTML` : tout passe par `h()` (texte inséré comme texte).
- Validations : `python -m pytest` (Chromium, Edge, Firefox ; `NAVIGATEURS=chromium` pour aller vite), `ruff check .`, `python -m vulture . --min-confidence 80`. Les captures d'écran des tests vont dans `captures/` : les regarder après un changement visuel.
- Format des données changé : incrémenter `VERSION_FORMAT` et continuer à lire les anciens fichiers (des exports circulent dans OneDrive).
- Ne jamais changer l'adresse du site (`nationaliste.github.io/forfaits`) : les données de chaque appareil sont liées à l'adresse, tout le monde devrait réimporter.
- Les suppressions sont des marques `supprime: true` (pas de retrait) : indispensable pour que la fusion propage les suppressions.
- `sw.js` sert la copie gardée puis la met à jour : une nouvelle version s'affiche à la 2e ouverture.
- Le dossier du projet est dans OneDrive : entre deux PC, passer par git (pull/push), pas par la synchro OneDrive du dossier `.git`.
- Couleurs : jamais de couleur en dur hors des variables de `:root`. Une nouvelle variable de couleur se déclare dans les deux palettes (`:root` pour le sombre, `:root[data-theme="clair"]` pour le clair) ; l'en-tête et les titres de fenêtre restent noirs dans les deux thèmes (`.entete, .dlg-tete` reprennent la palette sombre). Les tests mesurent le contraste de chaque palette : y ajouter la nouvelle association.
- Tableau Excel : `python outils/modele_excel.py` fabrique le modèle dans `prive/` (ignoré par git ; demande `pip install openpyxl`, sans lui `tests/test_modele_excel.py` est ignoré sans bruit). Ses titres de colonnes sont ceux de l'export CSV de l'outil et de `COLONNES_TABLEAU` (index.html) : en changer un, c'est changer les trois (`tests/test_modele_excel.py` et les tests d'import vérifient l'accord). L'ordre des familles est libre (l'import lit par titre) : dans le modèle, Boîtier et Installation sont à droite car elles servent rarement. Les éléments de départ de l'outil (`donneesInitiales()`) sont tous des exemples, retirés avec les forfaits d'exemple par « Supprimer les exemples » (sauf ceux qu'un vrai forfait utilise ou que l'utilisateur a retouchés, maj > 0 ; sur un appareil d'avant, sans la marque, ils sont reconnus à leur maj 0) : les listes du modèle sont donc vides, et un élément de départ qui ne serait pas un exemple devrait être repris dans `FAMILLES` du modèle (`tests/test_modele_excel.py` compare). L'import lit l'UTF-8 et l'ancien CSV d'Excel (Windows-1252), lit « / » comme « pas de données » (usage de l'équipe : même chose qu'une case vide : l'import ne crée jamais d'élément nommé « / »), garde l'identifiant d'un forfait dont la référence existe déjà, crée les familles (colonnes inconnues, 10 au maximum) et les éléments nouveaux après les avoir annoncés dans la fenêtre de confirmation, et n'écrase ni ne supprime rien d'autre.
- Premier remplissage : importer le tableau sur UN seul appareil, puis partager le `.json` aux autres (le même tableau importé sur deux appareils donne des identifiants différents, donc des doublons de référence). `prive/Forfaits-a-remplir.xlsx` est la saisie de l'utilisateur : `modele_excel.py` refuse d'écraser un fichier qui existe (pour un nouveau modèle, lui donner un autre chemin).
- Origine partagée : les données vivent dans le localStorage de `nationaliste.github.io`, commun à TOUS les sites GitHub Pages du compte. N'activer Pages sur aucun autre dépôt du compte et ne jamais créer le dépôt `nationaliste.github.io` (son `sw.js` contrôlerait aussi `/forfaits`) : ce site lirait ou effacerait les forfaits. Autre projet web : un autre hébergeur ou un autre compte.
- Surnoms : un surnom désigne une seule chose (nom d'un élément, surnom d'un autre élément ou forfait : refusé, partout où on en saisit : listes, formulaire, Mes surnoms, import du tableau). Ceux d'équipe sont dans les données (`surnoms`, exportés) ; les perso dans `forfaits.appareil.v1` (jamais exportés), et l'équipe gagne en cas de conflit. 3 surnoms au maximum : refusés avec un message au formulaire, aux listes et dans Mes surnoms (un élément qui en a déjà plus garde les siens tant qu'on n'en ajoute pas) ; l'import du tableau garde les 3 premiers et annonce les autres, pour que le même tableau donne le même résultat sur tous les appareils. La lecture des données en garde 10. Même surnom d'équipe sur deux choses (fusion de deux appareils) : le plus petit identifiant le garde, pour que tous les appareils donnent le même résultat quel que soit l'ordre de leurs listes. Les surnoms d'un élément entrent dans `parNom` : un nouveau contrôle sur les noms doit les prendre en compte.
- Total (« + Total » sur la carte, barre du bas, lignes libres) : par appareil dans `forfaits.appareil.v1` (`total`, jamais exporté, pas de changement de `VERSION_FORMAT`). Chaque ligne mémorise son nom et ses prix en centimes à l'ajout : un forfait modifié ou supprimé ensuite ne change ni ne casse le total. Sommes en centimes entiers, HT et TTC additionnés séparément (pas de recalcul TVA). 50 lignes, 99 par ligne au maximum.
- Carte d'un forfait (ordre voulu : nom, éléments, prix, référence) : le titre `h2.carte-nom` porte la désignation (les techniciens cherchent par nom), et la référence seulement si le forfait n'a pas de désignation. Un seul élément porte la classe `carte-ref` avec la référence : ce `h2`, ou le petit texte gris du pied — les tests s'en servent pour lire les cartes. Le nom de famille (`el-famille`) reste dans le DOM pour les lecteurs d'écran mais n'est plus affiché ; les filtres, eux, nomment les familles. TTC en rouge et en gros, HT en petit à côté, sur la même rangée que les boutons (`carte-bas`).
- Cartes repliées : par défaut une carte montre son nom et le TTC, le reste s'ouvre au premier appui (bouton `.carte-ouvrir`, `aria-expanded`, dans un `h2` — un `<button>` n'accepte ni `<h2>` ni `<div>` : tout ce qu'il contient est en `<span>`). Réglage par appareil (`compact` dans `forfaits.appareil.v1`, jamais exporté), bouton « Cartes entières » / « Liste compacte » à côté du tri. Les cartes ouvertes sont dans `etatUi.ouvertes` (en mémoire). Piège des tests : `tests/conftest.py` injecte `CARTES_ENTIERES` avant le chargement, sinon tout ce qui est dans le détail est caché ; un test du mode replié se crée avec `appareils(compact=True)`.
- Mode paysage : `@media (orientation: landscape) and (max-height: 540px)` aplatit en-tête, recherche et bandeaux pour garder des forfaits à l'écran ; la rotation est gérée par le CSS seul (rien en JS).
- Sécurité : la page publique ne contient aucun prix, donc rien de secret à y protéger ; ce qui l'est, ce sont les données (navigateur de chaque appareil, `.json` sur OneDrive). Un lien secret ne ferme pas un site statique public : un accès par appareil (idée roadmap#265) demande le serveur.
